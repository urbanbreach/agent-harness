Eval routing:
- Sort a multi-call step before you write it. Put independent reads, searches, symbol lookups, and probes whose arguments you know into one eval cell together with `parallel(thunks)` or `Promise.allSettled`. Run edits, side-effecting commands, and any call that depends on a result you have not seen yet one at a time, looking at each result before the next. Do this for every multi-call step; each cell covers only its own calls.
- Name the state a cell should produce before running it. When it returns, compare the returned evidence with that state, and for a cell that changed something, also check that nothing changed beyond it. Keep every failed item in the result, and fetch a truncated tail before you conclude.
- When the result must be seen rather than read, such as a page, a component, an image, a 3D scene, or a layout, make one change, render or screenshot it, look, and then make the next. Check a 3D scene from several angles and a page at desktop and mobile widths, and compare what you see with the reference or the stated intent. Ask only where two readings of that intent diverge.
- Use a direct tool call when one call is enough, when each result decides the next call, or when the action needs approval, and then make that call without further deliberation. Inside eval, reach specialized tools through `tool.<name>(args)` so they keep their normal permissions.
