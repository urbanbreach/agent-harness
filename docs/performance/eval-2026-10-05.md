# Native eval verification

Batch is removed from the tool registry, agent profiles, permissions, configuration,
and terminal rendering. Eval has no Batch alias.

The implementation is the Rust crate `harness-eval`. Rust owns cell scheduling,
deadlines, helper dispatch, metadata, output retention, and worker lifetimes.
JavaScript runs in embedded V8; Python, Ruby, and Julia use their installed
interpreters. Harness embeds its JavaScript runtime and needs neither Node nor Bun to
run eval. The reference checkout is used only by the comparison scripts.

## Logical checks

The same 54 cells run through the native public `Session` and the original
reference engine on both Node and Bun. All successful outputs match exactly;
all four intentional failures have the expected error outcome. Error wording
and stack paths vary between interpreters and are excluded from comparison.
The corpus covers persistence, declarations and destructuring, top-level await,
imports, files, Blob input, tool schemas, tool calls, completion, agents,
workpool adapters, parallel ordering and errors, pipelines, shell magic,
structured display, and recovery after errors.

Separate public-boundary tests exercise behavior outside that corpus:

- Detachment, FIFO queues, busy-reset refusal, stopping queued/running cells,
  execution and wall deadlines, steering, and one completion notification.
- Coordinator permissions, shared tool capacity, agent ownership, provider
  usage, MCP refresh, and reentrant kernel tools with scope and revision checks.
- Image forms and retention, output spilling, memory recycling, bounded status
  rows, and exact call totals after rich call metadata reaches its cap.

## Performance

The benchmark gate passes against both reference runtimes. The geometric mean
of the eight median-latency ratios is **0.760 versus Node** and **0.741 versus
Bun**, equivalent to 24% and 26% lower latency across this suite.

Median milliseconds, lower is better:

| Workload | Native Harness | Reference / Node | Reference / Bun |
| --- | ---: | ---: | ---: |
| JavaScript cold/reset | 41.512 | 51.881 | 40.968 |
| Python cold/reset | 110.754 | 141.259 | 138.025 |
| JavaScript array processing | 17.828 | 19.955 | 8.904 |
| Python computation | 19.851 | 19.734 | 19.993 |
| JavaScript pipeline | 1.497 | 2.120 | 3.662 |
| JavaScript output/spill | 2.897 | 5.279 | 5.126 |
| JavaScript tool calls | 2.147 | 1.173 | 2.387 |
| Python tool calls | 5.394 | 19.309 | 19.965 |

Individual differences remain. The JavaScript array workload takes about twice
as long as Bun; the small JavaScript tool-call workload takes 2.15 ms versus
Node's 1.17 ms. Python computation and JavaScript cold start are close to the
corresponding reference results. This is a suite-level performance result.

Measurements use ABC-CBA order, 62 warm samples per workload after warmups, and
10 cold/reset samples per language. Builds and other verification runs finish
before sampling. Native Harness uses the release worker and its public Session
API; the reference uses the reference session manager and eval tool with the
same immediate host callbacks. These timings exclude Harness coordinator and
full reference application overhead. This run measures Linux x86-64 latency; it does
not measure peak memory or other operating systems.

The [machine-readable report](eval-2026-10-05.json) includes medians, p95 values,
all conformance results, runtime versions, the source-tree hash, worker checksum,
and reference commit. Raw timing samples are in
`.omo/evidence/eval-native-performance-signoff/`. The reference checkout was clean
at commit `c196bc03276ce281e7d808959d6da55e177728ab`.
The implementation did not change during measurement. Report files were written
afterward.

Release builds use thin LTO. This keeps the embedded V8 runtime from requiring
a monolithic full-LTO link. Two existing terminal workloads passed after that
change, with 200 measured frames each. Resizing a 1,000-turn history measured
5.627 ms at p95; scrolling a 2,000-line viewer measured 0.652 ms. Both are below
the existing 8.333 ms frame-work budget. These measurements include input,
frame preparation, rendering, diffing, and ANSI encoding, but exclude terminal
emulator and display latency. Raw results are in
[`ui-resize.json`](../../.omo/evidence/eval-native-performance-signoff/ui-resize.json)
and [`ui-viewer.json`](../../.omo/evidence/eval-native-performance-signoff/ui-viewer.json).

A separate release run measured eval through the Harness coordinator, including
its permission and event handling. Each warm workload has 31 samples after three
warmups. This run used a local echo tool and no model requests. It is additional
Harness evidence, not the boundary used for the reference comparison above.

## Reproduction

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo nextest run --profile ci --workspace --all-features
HARNESS_EVAL_LANGUAGES=js,py,rb,jl scripts/test-lanes.sh eval
python3 scripts/check-test-suite-gates.py
bash scripts/harness-qa-dogfood.sh --self-test
node scripts/qa/capture-eval.mjs .omo/evidence/eval
node scripts/qa/benchmark-eval.mjs .omo/evidence/eval/performance
# Optional paired comparison with a separately supplied runner:
node scripts/qa/benchmark-eval.mjs .omo/evidence/eval/comparison "$REFERENCE_EVAL_RUNNER"
```

The additional release workloads use the existing test fixtures:

```sh
HARNESS_REWRITE_PERF_OUT="$PWD/target/eval-ui-resize.json" \
HARNESS_VIEWER_PERF_OUT="$PWD/target/eval-ui-viewer.json" \
cargo nextest run --profile perf --release -p harness-tui \
  --test rewrite_performance_test --test rewrite_viewer_performance_test \
  --test-threads 1
cargo build --release -p harness-eval --bin harness-eval-worker
HARNESS_EVAL_SIGNOFF=1 HARNESS_EVAL_LANGUAGES=js,py \
HARNESS_EVAL_PERF_OUTPUT="$PWD/target/eval-coordinator.json" \
cargo nextest run --profile perf --release -p harness-tools \
  --test eval --run-ignored all -E 'test(perf_eval)'
```

Four-language checks require the interpreters on PATH. The optional reference
comparison requires Node, Bun, and a standalone runner
passed as the second argument to `benchmark-eval.mjs`. The runner receives the
workload path, output path, and conformance path, and writes timing rows plus
`<output>.conformance.json`. It must use the same immediate host callbacks and
cell lifecycle. Supply any runner-specific interpreter dependencies separately.
GEM_PATH can select a custom Ruby gem installation. Visual capture uses Chromium
and the QA xterm.js dependencies. Final timing runs require no concurrent builds
or source edits.
